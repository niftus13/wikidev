- 상태: **확정** (2026-11-18, [6절](#6-미결-질문과-추천안) 추천안 A 승인)
- 설계 원본: Notion [WikiDocs형 블로그 플랫폼 설계안](https://app.notion.com/p/WikiDocs-41a2d703a2f881a7985eff5af6845fb1?source=copy_link) §1·§4·§6 (`/@{handle}` 사용자 공간)

## 1. 배경과 현재 상태

설계안에서 사용자 공간은 "플랫폼 → 사용자 공간 → 책" 구조의 중간 단계이다. URL은 `/@{handle}`이다.
API 일부는 구현됐지만 화면은 없다.

| 항목 | 상태 | 근거 |
| --- | --- | --- |
| 공간 조회 `GET /api/v1/spaces/{handle}` → `SpaceDto { id, handle, description }` | 구현 | `apps/api/src/services/auth.ts` `space()` |
| 공간 소개 수정 `PATCH /api/v1/spaces/{handle}` `{ description }` | 구현 | 소유자만 가능, 다른 공간은 404, 500자 초과는 400, CSRF 필요 |
| **공간의 공개 책 목록** | **없음** | `GET /api/v1/books`는 전체 공개 책만 반환하고 필터가 없다 |
| 공개 화면 `/@{handle}` | 없음 | `apps/web/app/pages/@[handle]/`에는 `[slug]/`만 있다 |
| 소개 편집 화면 | 없음 | 가입 시 소개는 빈 문자열로 생성된다 |
| 공간으로 가는 링크 | 없음 | 홈·검색·독서 화면에 `@handle`이 텍스트로만 표시된다 |

공간 조회 API는 handle을 소문자로 정규화하고(`normalizeHandle`), 비활성 사용자의 공간은 404를 반환한다.
반면 책 상세 `GET /spaces/{handle}/books/{slug}`는 소문자 handle만 받는다.

| 작업 | 에이전트 | 스킬 | 자동 적용 지침 |
| --- | --- | --- | --- |
| A. 공간 공개 책 목록 API | `backend-engineer` | `backend-feature` | `rules/backend.md`, `rules/testing.md` |
| B. 공개 공간 화면 | `frontend-engineer` | `frontend-feature` | `rules/frontend.md` |
| C. 공간 소개 편집 | `frontend-engineer` | `frontend-feature` | `rules/frontend.md` |
| D. 링크 연결·문서 | `frontend-engineer` | `frontend-feature` | `rules/frontend.md` |
| 완료 전 리뷰 | `quality-reviewer` | — | 읽기 전용 |

- 진행 순서는 A → B·C·D이다. B는 A의 계약에 의존한다.
- A는 새 엔드포인트만 추가한다. 기존 `GET /api/v1/books`의 계약은 바꾸지 않는다.
- 스키마 변경(migration)은 없다. 필요해지면 멈추고 사용자에게 확인한다.

## 3. 범위

### A. 공간 공개 책 목록 API (백엔드)

| ID | 요구사항 |
| --- | --- |
| A-1 | `GET /api/v1/spaces/{handle}/books`를 추가한다. 응답은 `PublicBookDto[]`로, 기존 공개 목록과 같은 형태이다. 정렬도 `created_at DESC, id DESC`로 같다. |
| A-2 | 삭제된 책과 비활성 사용자의 책은 제외한다. 공간이 없거나 비활성이면 **404**이다. 공간은 있지만 책이 없으면 **200 `[]`**이다. |
| A-3 | handle은 `normalizeHandle`로 정규화한다. 공간 조회 API와 같은 규칙이다. 형식이 잘못되면 404이다. |
| A-4 | route → controller → service → repository 계층을 따른다. 기존 `BookRepository.list()`의 SQL과 DTO 변환(`publicDto`)을 재사용한다. 중복 SQL을 만들지 않는다. |
| A-5 | `apps/api/test/books.test.ts`에 실제 MySQL 통합 테스트를 추가한다. 다룰 경우는 다음과 같다. |
| | 다른 공간의 책이 섞이지 않음, 삭제한 책 제외, 없는 handle 404, 대문자 handle 정규화, 책 없는 공간 `[]` |
| A-6 | README의 API 표에 계약을 추가한다. |

### B. 공개 공간 화면 `/@{handle}` (SSR)

| ID | 요구사항 |
| --- | --- |
| B-1 | `apps/web/app/pages/@[handle]/index.vue`를 만든다. 기존 `@[handle]/[slug]/` 경로와 충돌하지 않는지 확인한다. |
| B-2 | 서버 렌더링에서 `GET /spaces/{handle}`과 `GET /spaces/{handle}/books`를 함께 불러온다. 패턴은 기존 `@[handle]/[slug]/index.vue`의 `useAsyncData` + `useRequestFetch`와 같다. |
| B-3 | 표시 항목: `@handle`, 공간 소개, 공개 책 카드 목록(홈의 `book-card` 스타일 재사용). |
| | 소개가 비어 있으면 "소개가 아직 작성되지 않았습니다"를 보여준다. 책이 없으면 빈 상태를 보여준다. |
| B-4 | 공간 소개는 **일반 텍스트**로 렌더링한다. `v-html`과 Markdown은 쓰지 않고, 줄바꿈만 `white-space: pre-line`으로 살린다. |
| B-5 | 없는 공간이나 비활성 공간은 SSR 응답 상태 **404**이다. 그 외 오류는 503과 다시 시도 버튼이다. 기존 책 화면과 같은 방식이다. |
| B-6 | 대문자 handle(`/@Foo`)로 접근하면 정규화된 `/@foo`로 **301 리다이렉트**한다(6절 Q2). |
| B-7 | SEO 메타는 다음과 같다. 제목은 `@handle — WikiBlog`, 설명은 공간 소개의 앞부분(비어 있으면 기본 문구)이다. |
| B-8 | 로그인한 사용자가 **자기 공간**을 볼 때만 "소개 편집"과 "내 책 관리" 링크를 보여준다. |
| | 이 판단은 세션의 `space.handle`과 비교해 클라이언트에서만 한다. SSR HTML에는 넣지 않는다. 권한은 서버가 판단한다. |

### C. 공간 소개 편집

| ID | 요구사항 |
| --- | --- |
| C-1 | 편집 위치는 `/dashboard/books` 상단의 **내 공간** 패널이다(6절 Q1). 현재 handle, 공개 공간 링크, 소개 편집 폼을 둔다. |
| C-2 | 저장은 `PATCH /api/v1/spaces/{session.space.handle}`에 `{ description }`과 `X-CSRF-Token`을 보낸다. 성공하면 응답 `SpaceDto`로 화면 상태를 갱신한다. |
| C-3 | 글자 수 카운터를 둔다(`Array.from(text).length` 기준, 최대 500). 초과하면 저장을 막는다. 서버의 400도 안내한다. |
| C-4 | 기존 관리 화면의 패턴을 따른다: 중복 제출 방지, 실패 시 입력 보존, 401 안내와 "새 탭에서 로그인", 미저장 상태에서 이탈 확인. |
| C-5 | 저장하면 공개 공간에 **즉시 반영된다**는 점을 안내한다. |

### D. 링크 연결과 문서

| ID | 요구사항 |
| --- | --- |
| D-1 | 홈 책 카드, 검색 결과, 독서 화면 사이드바의 `@handle` 텍스트를 `/@{handle}` 링크로 바꾼다. |
| | 책 카드는 카드 전체가 링크이므로, 링크 안에 링크가 들어가지 않도록 구조를 확인한다. 어렵다면 카드 안의 handle은 텍스트로 둔다. |
| D-2 | `utils/paths.ts`에 `spacePath(handle)`를 추가하고 단위 테스트를 작성한다. |
| D-3 | README(화면과 URL, API 표, 작성자 화면 설명)와 history(체크포인트, 마일스톤, 검증 기록)를 갱신한다. Notion 설계안 §0·§6의 상태도 갱신한다. |

## 4. 범위 밖

- handle 변경(URL이 바뀌고 기존 링크가 깨짐), 프로필 이미지, 표시 이름
- 공간 소개의 Markdown 렌더링
- 공간 화면의 작성자 카테고리 필터와 책 목록 페이지네이션 (현재 공개 목록 API에도 없음)
- 팔로우, 구독, 통계
- 비공개 공간과 비공개 책 (책은 생성 즉시 공개라는 정책 유지)

## 5. 수용 기준

- [ ] `GET /api/v1/spaces/{handle}/books`가 해당 공간의 삭제되지 않은 책만 최신순으로 반환한다. 없는 공간과 비활성 공간은 404, 책이 없는 공간은 `[]`이다. 통합 테스트가 통과한다.
- [ ] `/@{handle}`이 SSR로 공간 소개와 책 목록을 렌더링한다. 없는 handle은 HTTP 404이다.
- [ ] `/@Foo`가 `/@foo`로 301 리다이렉트된다.
- [ ] 공간 소개의 HTML이나 스크립트가 실행되지 않고 텍스트로 표시된다.
- [ ] 소유자는 소개를 수정할 수 있고 공개 화면에 즉시 반영된다. 500자 초과는 저장이 막힌다. 다른 사용자의 handle로 보낸 PATCH는 404이다.
- [ ] 세션 만료와 저장 실패 시 입력이 보존된다. 미저장 상태에서 화면을 나가면 확인한다.
- [ ] 홈, 검색, 독서 화면에서 공간으로 이동할 수 있다.
- [ ] 다른 사용자가 공간을 볼 때 편집 링크가 보이지 않는다.
- [ ] 로딩, 빈 상태, 오류와 재시도, 키보드 조작, 모바일 화면을 확인했다.

## 6. 미결 질문과 추천안

각 질문의 **추천**을 기본안으로 삼는다. 승인되면 "결정"에 날짜를 적는다.

### Q1. 공간 소개 편집 위치

| 선택지 | 내용 |
| --- | --- |
| **A (추천)** | `/dashboard/books` 상단의 **내 공간** 패널에서 편집한다. |
| B | `/dashboard/space` 전용 화면을 만든다. |
| C | 공개 공간 화면 `/@{handle}`에서 소유자에게 인라인 편집을 제공한다. |

- **추천 이유**
  - 편집할 필드가 소개 하나뿐이다(500자). 전용 화면(B)은 과하다.
  - 내 책 관리는 로그인 후 처음 들어오는 화면이라 찾기 쉽다.
  - C는 공개 SSR 화면에 클라이언트 편집 상태를 섞게 된다. 그러면 캐시·SEO와 권한 표시가 복잡해진다.
- **영향**: handle 변경이나 프로필 같은 필드가 늘어나면 B로 옮긴다.
- 결정: **A** (2026-11-18 승인)

### Q2. 대문자 handle 처리

| 선택지 | 내용 |
| --- | --- |
| **A (추천)** | `/@Foo`를 `/@foo`로 301 리다이렉트한다. |
| B | 정규화된 내용을 그대로 렌더링한다(URL은 `/@Foo` 유지). |
| C | 404를 반환한다. |

- **추천 이유**
  - 공간 API가 이미 대소문자를 무시하므로, 같은 공간이 여러 URL로 색인되는 것을 막아야 한다.
  - 책 URL(`/@Foo/book`)은 지금 404이다. 리다이렉트를 하면 표준 URL이 하나로 정해진다.
- **영향**
  - 웹 SSR에서 `navigateTo(…, { redirectCode: 301 })`를 쓴다.
  - 책·페이지 URL의 대소문자 처리는 이번 범위에 넣지 않는다. 필요하면 후속으로 같은 방식을 적용한다.
- 결정: **A** (2026-11-18 승인)

### Q3. 공간 책 목록을 가져오는 방법

| 선택지 | 내용 |
| --- | --- |
| **A (추천)** | 새 API `GET /api/v1/spaces/{handle}/books`를 추가한다(3절 A). |
| B | 웹에서 `GET /api/v1/books` 전체를 받아 handle로 거른다(백엔드 변경 없음). |

- **추천 이유**
  - B는 공간 화면을 열 때마다 플랫폼 전체의 책을 전송한다. 책 수에 비례해 느려진다.
  - B는 공개 여부 판단을 웹에 일부 맡기는 셈이다.
  - A는 기존 `/spaces/{handle}/books/{slug}`와 경로 체계가 같다. 쿼리도 기존 `list()`에 조건 하나를 더하는 수준이다.
- **영향**: 백엔드 작업과 통합 테스트가 추가된다. 그래서 `backend-engineer`가 먼저 진행한다.
- 결정: **A** (2026-11-18 승인)
