## 1. 배경과 현재 상태

### 결함

로그인 재점검에서 확인한 내용이다. 웹 프록시(3000)를 거친 가입·로그인 요청이 **모두 웹 컨테이너 IP 하나로 요청 제한에 집계된다**.
Redis 키로 직접 확인했다: `auth-rate:login:172.21.0.5`.

- 전체 사용자 합산 15분 20회를 넘으면 **모든 사용자의 가입·로그인이 15분간 429로 막힌다**.
- 실패 로그인 20회만으로 서비스 전체 로그인을 막을 수 있다(서비스 거부).

### 원인

| 위치 | 현재 동작 |
| --- | --- |
| `apps/api/src/app.ts` | Express `trust proxy`가 설정되지 않았다. `request.ip`는 직전 연결 주소, 즉 웹 컨테이너 IP이다. |
| `apps/api/src/controllers/auth.ts` | `service.limit(request.ip, 'register' \| 'login')`로 Redis 키 `auth-rate:{action}:{ip}`를 만든다. |
| `apps/web/server/api/[...path].ts` | h3 `proxyRequest`가 클라이언트 요청 헤더를 거의 그대로 복사한다(`X-Forwarded-For` 포함). 프록시 자신은 클라이언트 주소를 붙이지 않는다. |
| `apps/web/nuxt.config.ts` | `nitro.devProxy['/api']`도 있다. 개발 서버(`nuxt dev`)에서는 이 경로가 `/api`를 처리할 수 있다. 그러면 개발과 운영의 프록시 코드가 다르다(확인 필요). |
| 웹 프록시 시간 제한 | 없다. API 컨테이너를 재빌드하는 동안 프록시를 거친 로그인 요청이 2분 넘게 응답 없이 대기했다. |

### 주의

API에서 `trust proxy`만 켜면, 브라우저가 보낸 `X-Forwarded-For`가 그대로 전달되므로 **누구나 IP를 위조해 요청 제한을 우회할 수 있다**.
따라서 **프록시가 헤더를 다시 쓰는 일**과 **API가 믿을 hop을 좁히는 일**을 함께 해야 한다.

### 운영 마일스톤의 나머지 (이번 범위 밖, 후속 체크포인트)

1. CI: 타입 검사, 빌드, 단위 테스트, MySQL·Redis 통합 테스트
2. E2E: 독자·작성자 흐름 (브라우저 실행 환경 포함)
3. 운영 배포: HTTPS, `COOKIE_SECURE=true`, 리버스 프록시, 시크릿 관리
4. 백업·복구와 로그·모니터링

## 3. 범위

### A. API: 신뢰할 프록시만 믿고 클라이언트 IP 사용

| ID | 요구사항 |
| --- | --- |
| A-1 | 환경 변수 `TRUST_PROXY`를 추가하고 `config.ts`에서 검증한다. 값은 IP·CIDR 목록이나 `loopback`, `linklocal`, `uniquelocal`만 허용한다. `true`, 숫자 hop 수, `*`처럼 모든 주소를 믿는 값은 **시작 시 오류**로 막는다. |
| A-2 | 값이 없으면 지금처럼 `trust proxy`를 끈다(하위 호환). 설정되면 `app.set('trust proxy', <검증된 목록>)`을 적용한다. |
| A-3 | 요청 제한 키에는 Express가 계산한 `request.ip`를 그대로 쓴다. IPv4가 IPv6 형식(`::ffff:a.b.c.d`)으로 들어오면 IPv4로 정규화해 같은 클라이언트가 두 키로 나뉘지 않게 한다. |
| A-4 | 신뢰하지 않는 주소에서 온 `X-Forwarded-For`는 무시된다. Express의 `proxy-addr` 동작이다. 이를 테스트로 고정한다. |
| A-5 | 테스트는 DB 없이 돌아가는 단위 테스트로 작성한다. 방식은 다음과 같다. |
| | `createApp`에 키를 기록하는 가짜 Redis를 넣고 임시 포트에 띄운다. 설정별로 아래를 검증한다. |
| | ① `TRUST_PROXY` 미설정이면 XFF를 무시한다. ② loopback을 신뢰하면 XFF의 클라이언트 주소로 키가 나뉜다. ③ 위조한 다단 XFF는 신뢰 hop 다음 주소만 쓴다. ④ 잘못된 `TRUST_PROXY` 값이면 시작에 실패한다. |

### B. 웹 프록시: 헤더 재작성, 시간 제한, 경로 하나로

| ID | 요구사항 |
| --- | --- |
| B-1 | 먼저 `nuxt dev`에서 `/api` 요청이 `devProxy`와 `server/api/[...path].ts` 중 어디서 처리되는지 확인하고 보고한다. |
| B-2 | 프록시 경로를 하나로 통일한다(7절 Q3). 개발과 운영이 같은 서버 라우트 코드를 쓰게 한다. |
| B-3 | 프록시는 클라이언트가 보낸 `X-Forwarded-For`, `X-Real-IP`, `Forwarded`를 **버리고**, 자신이 본 연결 주소(`event.node.req.socket.remoteAddress`)로 `X-Forwarded-For`를 새로 만든다. |
| | 웹 앞에 리버스 프록시를 두는 운영 구성은 운영 배포 체크포인트에서 다룬다. 이번에는 웹이 첫 hop이라고 가정한다. |
| B-4 | 헤더를 만드는 로직은 순수 함수(`server/utils/` 등)로 분리하고 단위 테스트를 작성한다. 위조 헤더 제거, 기존 쿠키·CSRF·Origin·Content-Type 헤더 유지를 검증한다. |
| B-5 | 프록시 요청에 시간 제한을 둔다(7절 Q2). 넘으면 **504**와 JSON `{ "error": "Upstream timeout" }`을 반환한다. 웹의 `apiErrorStatus` 처리와 충돌하지 않는지 확인한다. |
| B-6 | SSR 내부 호출(`useRequestFetch`)도 같은 프록시를 거친다. 이 호출에서 쿠키 전달과 공개 화면 SSR이 그대로 동작하는지 확인한다. |

## 5. 수용 기준

- [ ] 웹 프록시를 거친 서로 다른 클라이언트의 로그인이 서로 다른 요청 제한 키로 집계된다. 한 클라이언트가 429를 받아도 다른 클라이언트는 로그인할 수 있다.
- [ ] 클라이언트가 보낸 `X-Forwarded-For`로 요청 제한 키를 바꿀 수 없다. 웹 경유와 API 직접 호출 모두 해당한다.
- [ ] `TRUST_PROXY`를 설정하지 않으면 지금과 같이 동작한다. 모든 주소를 믿는 값은 시작할 때 거부된다.
- [ ] 개발과 운영의 `/api` 프록시가 같은 코드를 쓰고, 시간 제한을 넘으면 504를 반환한다.
- [ ] 기존 기능에 회귀가 없다: 로그인·세션·로그아웃, CSRF, Origin 검사, 공개 SSR, 작성자 화면 요청.
- [ ] 새 단위 테스트가 통과하고, 기존 웹 테스트와 API 통합 테스트가 모두 통과한다.
- [ ] README, `.env.example`, history에 설정과 위험이 기록되어 있다.

## 6. 검증

```bash
pnpm build:libs
pnpm typecheck
pnpm --filter @wikiblog/api test                  # 새 단위 테스트(DB 불필요) 포함
pnpm --filter @wikiblog/web typecheck
pnpm --filter @wikiblog/web test
docker compose -p wikiblog-wt up --build -d
docker compose -p wikiblog-wt exec -T -e INTEGRATION_TESTS=1 api pnpm --filter @wikiblog/api test
```

- 실제 스택에서는 웹 프록시를 거쳐 확인한다. 위조한 `X-Forwarded-For`를 붙인 로그인 실패 요청을 보내고 Redis의 `auth-rate:*` 키를 읽어 본다(읽기 전용).
- 요청 제한 카운터를 지우거나 우회하지 않는다. 429를 재현할 때는 반드시 남는 카운터를 고려한다. 재현은 테스트 전용 Redis나 단위 테스트로 한다.

## 7. 미결 질문과 추천안

### Q1. 클라이언트 IP를 전달하고 신뢰하는 방식

| 선택지 | 내용 |
| --- | --- |
| **A (추천)** | 웹 프록시가 XFF를 자신이 본 주소로 **다시 쓴다**. API는 `TRUST_PROXY`로 지정한 주소만 신뢰한다. Compose에서는 웹 컨테이너가 속한 네트워크 대역을 지정한다. |
| B | 웹 프록시와 API가 공유 비밀값으로 서명한 전용 헤더(`X-Client-IP` + HMAC)를 쓴다. |
| C | 요청 제한을 웹 서버로 옮긴다. 웹이 클라이언트 주소를 직접 본다. |

- **추천 이유**: Express 표준 기능(`proxy-addr`)을 그대로 쓰므로 직접 구현할 보안 코드가 가장 적다. 운영에서 리버스 프록시를 앞에 두는 구성으로도 확장할 수 있다.
  - B는 비밀값 배포와 교체가 추가로 필요하다.
  - C는 정책의 원본을 API에 두는 원칙(설계안 §12)에 어긋난다.
- **영향**: Compose 네트워크 대역이 바뀌면 `TRUST_PROXY`도 바꿔야 한다. `uniquelocal`(사설 대역 전체)은 설정이 쉽지만 신뢰 범위가 넓다. 그래서 **대역을 명시하는 것**을 기본으로 한다.
- 결정: **A** (2026-11-18 승인)

### Q2. 웹 프록시 시간 제한

| 선택지 | 내용 |
| --- | --- |
| **A (추천)** | 30초, 넘으면 504 |
| B | 10초 |
| C | 두지 않음(현행) |

- **추천 이유**
  - 현재 가장 무거운 요청도 수 초 안에 끝난다. 본문 저장(16KB)과 검색 50건이 그 예다.
  - 30초면 정상 요청을 끊지 않으면서, 2분 넘게 매달리는 일은 막는다.
  - 10초는 개발 중 재빌드나 콜드 스타트 때 오탐이 생길 수 있다.
- **영향**: 값은 런타임 설정 `NUXT_API_PROXY_TIMEOUT_MS`로 바꿀 수 있게 한다.
- 결정: **A** (2026-11-18 승인)

### Q3. 개발 프록시 경로 통일

| 선택지 | 내용 |
| --- | --- |
| **A (추천)** | `nuxt.config.ts`의 `nitro.devProxy['/api']`를 제거한다. 개발에서도 `server/api/[...path].ts`를 쓴다. |
| B | 두 경로를 유지하고 `devProxy`에도 같은 헤더 처리를 설정한다. |

- **추천 이유**: 보안 헤더 처리를 한 곳에서만 구현하고 테스트할 수 있다. 개발 환경에서 검증한 동작이 운영과 같아진다.
- **영향**
  - B-1 확인 결과 `devProxy`가 실제로 쓰이지 않으면, 제거만 하고 동작은 바뀌지 않는다.
  - 쓰이고 있었다면 개발 중 핫 리로드와 쿠키 동작을 다시 확인한다.
- 결정: **A** (2026-11-18 승인)
