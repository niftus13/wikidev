# 운영 배포 체크리스트 (요구사항 작성 전)

- 작성: 2026-11-18
- 상태: **체크리스트**. 운영 배포 체크포인트를 시작할 때 이 목록을 바탕으로 요구사항을 확정한다.
- 결정 배경: 운영 환경에 **리버스 프록시와 CDN**을 둔다(2026-11-18 사용자 결정).
- 배포 대상: **AWS EC2 인스턴스**(2026-11-18 사용자 결정). 아래 6절에 EC2 관련 확인 항목을 정리했다.
  운영 1은 "웹(Nuxt)이 첫 hop"이라는 가정으로 구현했다. 따라서 클라이언트 IP 신뢰 체인을 **운영 배포에서 다시 설계**한다.

## 1. 운영 1에서 바뀌어야 하는 가정

| 운영 1 구현 (`docs/checkpoints/ops-proxy-rate-limit.md`) | 리버스 프록시·CDN 도입 후 문제 |
| --- | --- |
| 웹 프록시가 클라이언트의 `X-Forwarded-*`·`X-Real-IP`·`Forwarded`를 **모두 버리고**, 직접 본 소켓 주소로 XFF를 새로 쓴다 | 웹이 보는 소켓 주소는 리버스 프록시 주소이다. 그러면 모든 사용자가 다시 **하나의 요청 제한 키**로 모인다(운영 1 이전 결함의 재발). |
| API의 `TRUST_PROXY`는 웹 컨테이너 주소 하나 | 웹이 상위 hop의 정보를 버리므로, API가 신뢰 범위를 넓혀도 실제 클라이언트 주소를 알 수 없다. |
| 개발 서버 첫 hop 재작성(`nuxt.config.ts`의 `devServerHandlers`) | 운영 빌드에서는 쓰이지 않는다. 운영 경로를 따로 검증해야 한다. |
| 프록시 시간 제한 30초(504) | CDN·리버스 프록시의 시간 제한과 순서를 맞춰야 한다. 바깥 hop이 더 길어야 504가 제대로 전달된다. |

## 2. 신뢰 체인 재설계 체크리스트

- [ ] 배포 구조를 확정한다: `클라이언트 → CDN → 리버스 프록시(TLS 종료 위치) → Nuxt 웹 → API`. hop마다 주소와 네트워크를 정한다.
- [ ] CDN이 실제 클라이언트 주소를 어떻게 전달하는지 확인한다(XFF 추가 방식인지, 전용 헤더인지). 제공자의 문서를 기준으로 한다.
- [ ] 리버스 프록시는 **CDN에서 온 요청만** 클라이언트 주소 헤더를 믿는다. 기준은 CDN IP 대역 목록이나 오리진 인증(헤더·mTLS)이다. 그 밖의 요청이 보낸 헤더는 버린다.
- [ ] **CDN을 우회해 오리진에 직접 접속하는 것을 막는다**: 방화벽, 보안 그룹, 오리진 인증 중에서 정한다.
- [ ] 웹 프록시의 헤더 처리를 "모두 버림"에서 바꾼다. **신뢰하는 직전 hop(리버스 프록시)에서 온 요청만** XFF를 이어받고, 신뢰하지 않는 hop에서 온 값은 버린다.
  - 이 신뢰 설정은 API의 `TRUST_PROXY`와 같은 형식의 웹 설정으로 둔다. trust-all 값은 거부한다.
- [ ] API의 `TRUST_PROXY`를 다시 정한다. 웹만 신뢰하고 웹이 정제한 XFF를 받을지, 체인 전체를 신뢰할지 정한다. 위조한 다단 XFF 테스트를 새 구조에 맞게 갱신한다.
- [ ] 요청 제한 위치를 정한다: API만 할지, CDN·WAF에도 둘지. 계정 기준 제한(미결 정책)과 함께 검토한다.
- [ ] 바깥 hop부터 시간 제한을 크게 둔다(CDN > 리버스 프록시 > 웹 30초). 504와 오류 페이지가 어떻게 보일지 정한다.
- [ ] 실제 스택에서 검증한다: 위조 헤더를 직접 보냈을 때, CDN 경유와 오리진 직접 접속 각각의 요청 제한 키를 확인한다.

## 3. CDN 캐시 정책 체크리스트

- [ ] `/api/*`는 캐시하지 않는다. API는 이미 `Cache-Control: no-store`를 보낸다. CDN이 이를 따르는지 확인한다.
- [ ] `Set-Cookie`가 있는 응답, 로그인·가입·대시보드(`/dashboard/**`, `/login`, `/register`)는 캐시하지 않는다.
- [ ] 공개 SSR(`/`, `/@{handle}`, 책·페이지, 검색)은 정책이 "즉시 반영"이다. 책 생성, 책 분류, 공간 소개, 발행이 모두 해당한다. 그래서 캐시 TTL을 어떻게 정할지 결정한다.
  - 선택지는 짧은 TTL, 발행 시 무효화(purge), 캐시하지 않음이다. 발행 취소 정책이 미결이라는 점도 고려한다.
- [ ] 쿠키나 세션에 따라 내용이 달라지는 SSR이 공유 캐시에 저장되지 않는지 확인한다. 지금은 소유자 링크를 클라이언트에서만 표시한다.
- [ ] 정적 자산(`/_nuxt/*`)은 해시 파일명이므로 길게 캐시한다.

## 4. HTTPS·보안 설정 체크리스트

- [ ] `APP_ORIGIN`을 HTTPS 운영 도메인으로, `COOKIE_SECURE=true`로 설정한다. `config.ts`가 이미 HTTPS 조합을 강제한다.
- [ ] CDN과 리버스 프록시가 `Origin` 헤더를 그대로 전달하는지 확인한다. API는 변경 요청에서 Origin을 검사한다.
- [ ] HSTS와 TLS 설정, HTTP에서 HTTPS로의 리다이렉트를 설정한다.
- [ ] 운영은 `nuxt dev`가 아니라 `nuxt build` 결과를 실행하도록 이미지와 Compose(또는 배포 매니페스트)를 만든다. 소스 마운트도 제거한다.
- [ ] MySQL·Redis는 외부에 공개하지 않는다. 시크릿 관리 방식을 정한다(`.env` 파일을 쓸지, 시크릿 저장소를 쓸지).
- [ ] 헬스 체크(`/api/health`)를 외부에 노출할지 정한다.

## 5. 백업·관측 (운영 4와 연결)

- [ ] MySQL 백업과 복구 연습, 마이그레이션 실패 시 되돌리는 절차
- [ ] API·웹 로그에 남길 클라이언트 주소 기준(신뢰 체인 결과)과 개인정보 보존 기간
- [ ] 요청 제한 429 발생량, 504 비율, 헬스 체크 실패를 모니터링한다

## 6. EC2 배포 확인 항목

- [ ] **운영용 이미지와 Compose를 만든다.** 지금 `Dockerfile`과 `compose.yaml`은 개발용이다(`nuxt dev`, 소스 마운트).
  - 웹은 `nuxt build` 결과(`.output/server/index.mjs`)를 실행하고, API는 운영 환경 변수로 실행하는 운영용 구성이 필요하다.
- [ ] 인스턴스 아키텍처(x86_64 또는 arm64/Graviton)에 맞춰 이미지를 빌드한다.
  - 빌드 위치를 정한다: CI에서 빌드해 레지스트리(ECR 등)에 올릴지, EC2에서 직접 빌드할지.
  - EC2에서 빌드한다면 `nuxt build`의 메모리 사용량에 맞춰 인스턴스 크기나 swap을 정한다.
- [ ] 배포 구조의 AWS 매핑을 정한다. CDN은 CloudFront 등을, 리버스 프록시는 ALB나 인스턴스 안의 nginx 중에서 고른다. TLS 인증서(ACM이나 certbot)도 정한다.
  - 그에 맞춰 2절의 클라이언트 IP 헤더를 확정한다(CDN 전용 헤더 또는 ALB의 XFF 추가). 그리고 웹·API의 신뢰 주소를 다시 설계한다.
- [ ] 보안 그룹:
  - 인스턴스나 ALB에는 CDN·리버스 프록시 경로의 80/443만 연다. CloudFront를 쓰면 관리형 prefix list나 오리진 인증 헤더를 쓴다.
  - SSH는 관리자 IP나 SSM Session Manager로 제한한다.
  - MySQL·Redis·API(4000)·웹(3000) 포트는 외부에 열지 않는다.
- [ ] 데이터 저장소를 정한다.
  - MySQL: EC2 안 컨테이너와 EBS 볼륨, 또는 RDS
  - Redis: 컨테이너, 또는 ElastiCache
  - 백업(EBS 스냅샷이나 RDS 자동 백업)과 복구 연습을 5절과 연결한다.
- [ ] 시크릿(MySQL 비밀번호 등)은 인스턴스의 `.env` 파일이 아니라 SSM Parameter Store나 Secrets Manager에서 주입하는 방식을 검토한다.
- [ ] Compose 전용 네트워크 대역(`WEB_API_SUBNET`, 기본 `10.231.0.0/29`)이 VPC CIDR이나 피어링 대역과 겹치지 않는지 확인한다. 겹치면 `.env`에서 바꾼다.
- [ ] 배포·롤백 절차를 정한다: 이미지 태그, 마이그레이션 실행 시점, 헬스 체크(`/api/health`) 기반 확인. 로그 수집(CloudWatch 등)도 정한다.
